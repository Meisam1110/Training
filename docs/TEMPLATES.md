# Letter templates (Dev-B)

Six `.docx` templates live in `templates/`; they are generated by `python templates/build_templates.py` from the wording in `backend/app/documents/wording.py` (the same wording feeds the e-mail HTML body, so docx and e-mail never diverge). Templates contain only `{{placeholders}}`: no real names, national IDs, phones, e-mails, employee/invoice/ticket/letter numbers, no macros, no mail-merge data-source links, no drive paths. Images (Irancell-look banners, letterhead, logo, how-to screenshots) are in `templates/assets/`.

## Rendering rules

- Syntax `{{name}}`; `{{name|fa}}` converts digits to Persian (renderer option `persian_digits`, default on; per-call override with field `persian_digits: false`) and isolates numeric runs left-to-right so `10:00-16:00` is not reversed in RTL text; `{{name|ltr}}` isolates phones/e-mails.
- Tables: a row containing `{{list.field}}` is repeated per item; `{{list._n}}` is the 1-based row number.
- Strict: a required field that is missing or blank raises `MissingFieldError` naming it (list items as `participants[2].phone`). Optional fields use their documented default; an optional signature line that is empty is removed (no blank lines).
- Values are inserted as plain text (docx) or HTML-escaped (email); only http(s) URLs become links in the e-mail body. Substitution is single-pass over the template: `{{...}}`, `{%`, `${` inside DATA are literal text and never re-interpreted (braces are shielded during the run and restored at the end); NUL/C0/C1/surrogate characters are stripped.
- Filters: `|fa` Persian digits + LTR isolation of numeric runs, `|ltr` LTR isolation (phones/e-mails), `|iso` first-strong isolate for mixed-script values (Persian day names inside an English line).
- `lang` (`fa`/`en`/`both`) selects language sections of bilingual kinds (course_announcement, level3_request, level3_manager_check); other kinds ignore it. `required_fields(kind, lang)` respects it.
- Raw inputs may replace derived text fields: `start_date`, `deadline_date`, `letter_date` (ISO `yyyy-mm-dd` or `date`), `duration_hours`, `gender` (`male|female`; `manager_gender`, `reporter_gender` for the manager check). Explicit text fields always win over derived ones.
- Organisation constants can be set once in `templates/letter_defaults.json` (see `letter_defaults.example.json`); such fields drop out of `required_fields()`.
- Fixes vs. legacy: one wording per template, spelling «گفتگو» (legacy had «گغتگو»), «همکاران گرامی», deadline/days/time only from fields, «has attended» grammar, no hard-coded course/date/person.

### Notes per kind

- `course_announcement`: `Time_Farsi`/`Duration` include the unit (`۱۲ ساعت` / `12 Hours`); `Sessions_Count` is a number (the template adds «جلسه»). Legacy fields `Time`, `Sessions_Count` are shared by the fa and en sections.
- `institute_letter`: participants table carries personal data by nature (national ID, phone); it is filled at render time only and never stored in a template.
- `settlement_letter`: canonical names are Core's (`start_date_gregorian`, `invoice_total`, `attendees[].label`); the alternative spellings `start_date_greg`, `total`, `rows`, `description` are accepted too, and `required_fields()` omits aliased fields so either spelling passes a pre-check (render() still names any that are absent). Each row shows its exact share in an `Amount` column (exact split, remainder to the first rows, always summing to the total); `per_attendee` is labelled "base share". `supplier_code` is optional (`-` when the supplier has none, as in the legacy sheet).
- `line_manager_approval`: at most 9 rows per letter; use `automation.batch_by_manager`. Legacy `Empname1..9/EmpSummary1..9/EmpTicket1..9` are still accepted and flattened into `employees`.
- `level3_manager_check`: the legacy typo `Reporter_F_tilte` stays canonical (matches docs/ANALYSIS.md); `Reporter_F_title` is accepted as an alias.
- Removed from the legacy sheets: hard-coded personal phone/e-mail in the sign-off (now `signer_*`, optional), embedded workbook links (drive-letter paths), VBA and recipient data.

## Privacy audit of templates/ (round 2)

Checked: (a) every file in `templates/assets/` and every image embedded in the six `.docx` (viewed each one); (b) for every `.docx`: `word/document.xml`, headers/footers, `docProps/core.xml` + `app.xml`, `customXml`, comments (none exist), thumbnails, relationships; text parts were scanned for e-mail addresses, numbers of 7+ digits and non-example URLs (`tests/integrations/test_documents.py::test_template_has_no_macros_links_or_personal_data` keeps enforcing the text/macro part).

Found and changed:
- `banner_engagement_fa/en.png` were photographs of two real people (faces) -> **replaced** by banners derived from the face-free "Grow with purpose" artwork with the team name re-typeset (Vazirmatn / DejaVu). No photo remains.
- `howto_ticket.png` was a real iCare screenshot (an internal ticket key and a user avatar) -> **redrawn** as a synthetic mock (`LMS-000000`, "Sample request").
- `docProps`: author/last-modified-by set to the neutral `TMS`, fixed creation date, no company, keywords or category. The generic python-docx thumbnail is blank white; `customXml` holds only an empty bibliography stub.

Checked and kept (no personal data): `howto_level3_form.png` (form with generic "Test" text), `howto_manager_agree.png` (Yes/No form with a Persian instruction callout), `banner_talent_fa/en.png` (artwork + team name), `logo_irancell.png` (company logo), `letterhead_top/bottom.jpg` (company letterhead: corporate name, public head-office address, switchboard/fax numbers and web address - organisational, not personal).
Result: no personal names, faces, e-mails, employee/ticket/invoice/letter numbers or personal phones in templates, assets or document metadata. Limits: this is a visual + pattern audit by the author, not an independent review; the company letterhead intentionally keeps the corporate contact line.
